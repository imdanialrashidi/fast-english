# Current Implementation Plan — Fast English Podcast MVP

## Goal and non-goals
- Goal: deliver the most complete verifiable MVP in five phases (0–4) by end of 2026-07-30: Persian-first English-learning product with manual payment, operator review, placement, lessons+audio, PWA + APK, static landing.
- Non-goals: CEFR certification, SMS OTP, email verification, self-service password recovery, payment/landing crossover, CMS, SSR, GraphQL, microservices, Docker, Next.js/Astro.

## Facts, constraints, and assumptions
- Repo is a clean scaffold on `main` (commit 6e9f939); no app code, no lockfile, no `server/`/`android/`.
- Local: Node v22.23.1, pnpm 11.3.0, adb 1.0.41. CI: Node 24.
- `.gitignore` must add `server/pb_data/` (currently only watcher/permission-denied, not ignored).
- PocketBase `PasswordAuth.IdentityFields` is configurable → `phone` is a native identity field (Context7-verified).
- Exact dependency versions pinned at Phase 0 via Context7 + generated lockfile (no lockfile exists yet).
- Assumption: package ID `com.fastenglishpodcast.app` (reversible).
- Assumption: receipt max 5 MB unless repo/deploy evidence requires lower.
- Hard deadline = prioritization constraint; security invariants never downgraded.

## Existing components/patterns to reuse
- `scripts/verify.sh` (dispatcher; will add `scripts/project-verify.sh`), `scripts/ci-install.sh`, `.github/workflows/quality.yml`.
- `opencode.jsonc` plan-agent edit allowlist for docs; `risk-review` skill for `/review`.
- Workflow: `/plan` → `/build` (one slice/session) → `/review` (sensitive) → `/ship`.

## Smallest viable design and data/control flow
- Single pnpm package, two Vite configs (`vite.landing.config.ts`, `vite.app.config.ts`), outputs `dist-landing/` + `dist-app/`; Capacitor `webDir=dist-app`.
- PocketBase: `users` auth collection (phone identity), `plans`, `payment_requests`, `subscriptions`, `placement_attempts`, `placement_questions` (versioned), `topics`, `lessons`, `progress`; JS migrations + hooks for authz/transactions/grading.
- Env-aware API-base resolver (browser origin / Android explicit HTTPS / dev proxy / adb reverse).

## Risks and controls
- Security: client tampering of role/price/status → server ignores client-set protected fields; tests for tampering.
- Payment idempotency: double approval → unique subscription→request link + transaction; test repeated approval.
- Receipt privacy: public URL leak → protected file field, randomized name, no logs; test unauthorized access.
- Placement answer leakage: client never receives correct answers; test 20-question flow + duplicate submit.
- Premium denial: direct API by pending/expired → server-side check; test deny/allow.
- APK origin confusion: bundled APK ≠ browser origin → explicit HTTPS API base; test device connectivity.
- Two-day feasibility: content (lessons/questions/audio) and prices are external inputs → fixtures for dev/test only; mark unverified items in final report.
