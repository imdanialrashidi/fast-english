# Automated Production Release Pipeline — Fast English Podcast

Status: active — plan only (no production mutation)
Updated: 2026-08-26

## 1. Goal and non-goals

**Goal:** Implement a production-safe, minimally manual release pipeline so that *verified* changes merged to `main` can automatically build immutable artifacts, deploy the exact verified commit to the appropriate Coolify production surfaces (via GHCR `sha-<commit>` pinning), preserve PocketBase data/backup/migration contracts, and — only when an intentional Android version bump is present — build/sign/verify and atomically publish a new APK under `https://fastenglishpodcast.com/releases/` without rebuilding the Landing. The Landing's existing runtime fetch of `/releases/release-metadata.json` is the APK source of truth.

**Non-goals:**
- No automatic deploy from pull requests, unverified commits, or red/missing canonical quality gates.
- No new infrastructure beyond the accepted Coolify Cloud + owned VPS + GHCR + SSH host path; no second public proxy.
- No rebuilding the Landing solely to change its APK download URL/version — runtime metadata handles it.
- No committing keystore bytes/passwords, no secrets in logs/bundles/summaries, no debug-key or unsigned APK publication.
- No overwriting an existing released APK filename with different bytes, no broadening `/_/` or Landing `/api/*`.
- No destructive auto-recovery from migration failures; no database rollback without explicit backup-restore policy.
- No deployment to real production in this plan phase without separate explicit owner authorization.

## 2. Acceptance criteria (observable, with proof required)

- **A1 — Automated verified-main to production (no manual Coolify interaction).** Push/merging a green commit to `main` automatically: waits for the canonical `quality` `verify` gate for that exact SHA to be green, builds immutable `ghcr.io/<owner>/fast-english/{landing,app,admin,pocketbase}:sha-<12>` images, PATCHes the affected Coolify applications to that exact SHA tag (immutable — not the moving `production` alias), triggers Coolify deploy, polls to `finished`, then passes independent public HTTPS health (`scripts/prod-health-check.sh`) and existing `deploy/smoke-prod.sh` (quick or full). Failure of any gate reports RED and stops. Proof: CI run on a `main` push where `quality` is green, followed by the new release workflow run (logs + job summary) showing resolved SHA, quality-gate check, per-surface Coolify `deployment_uuid` poll to `finished`, health + smoke PASS, pinned tag evidence (`docker_registry_image_tag = sha-…`).
- **A2 — Red/missing quality cannot reach production.** A commit whose `quality` `verify` check-run is missing/red/cancelled is refused before any build/deploy/publish step runs. Proof: forced push of a branch with a deliberately failing `verify` lane → release workflow exits with `status=blocked` and no GHCR publish or Coolify trigger; job summary shows the refusal.
- **A3 — Immutable-tag deployment (eliminate moving-alias ordering).** Production Coolify applications' runtime image is `sha-<commit>` of the commit that passed verification. The moving `production` alias, if retained, is updated only *after* health+smoke pass and is never the source Coolify pulls at deploy time. Proof: Coolify API PATCH payload captured in logs (`docker_registry_image_tag: sha-…`), GHCR tag listing shows both SHA and — post-verification — `production` pointing to same digest; redeploy without the PATCH cannot advance production.
- **A4 — Selective surface deployment preserves PocketBase data.** A frontend-only change (landing/app/admin) does not restart or mutate the PocketBase container or `/opt/fast-english/shared/pb_data`. Proof: `scripts/release-classify.sh` classification (A-only) → workflow deploys only those surfaces; Coolify deployment history shows no `pocketbase` deployment; `tests/infra` persistence proof + `prod-health-check` still shows PB healthy with prior data; no pre-deploy backup triggered for A-only.
- **A5 — Backend/migration backup, concurrency, and recovery.** Any release classified B (hooks) or C (migrations) takes a verified pre-deploy backup on the host via SSH (`FEP_SSH_*`) and verifies `FEP_CHECK_OFFSITE`; migrations are flagged as C with the non-reversibility warning; concurrent production releases are serialized (no overlap). Proof: B/C release log shows `backup.sh` + `backup-copy.sh` artifact path + off-VPS check; second push while first production run is in_progress is queued (concurrency group `release-production`); rollback docs remain authoritative (image swap only; migration recovery = restore pre-deploy backup).
- **A6 — Intentional Android release publishes atomically without Landing rebuild; ordinary commits and failures leave prior release intact.** When `android/app/build.gradle` (and matching `capacitor.config.json`/`package.json` per `scripts/check-android-version.mjs`) shows a strictly increased `versionCode` and matching `versionName` vs. the last published `release-metadata.json`, the pipeline validates consistency (`android:check:version`), builds the signed Release APK only with `FEP_ANDROID_*` Environment secrets (fails safely without them), runs `scripts/verify-release-apk.sh` (apksigner/zipalign/aapt/SHA-256), uploads via SSH to a staging path (`/opt/fast-english/shared/releases/.staging/`), verifies integrity on-host (sha256+size match, no existing filename collision with different bytes), atomically moves to final (`mv -Tf` with metadata moved last), and verifies public HTTPS APK + metadata SHA/size. Landing is not rebuilt. If `versionCode` was not strictly increased or is invalid, web deployment may proceed but the Android job is skipped (not failed) and prior APK/metadata stay byte-identical. If any Android gate fails (signing missing, apksigner/zipalign/aapt/SHA mismatch, collision, staging or public verification mismatch), the workflow fails closed: staging cleaned up, no host file overwritten, prior metadata remains served; web success is reported independently. Proofs: (i) version-bump commit → staging upload + host `sha256sum` match + public `curl https://fastenglishpodcast.com/releases/<file>` SHA/size/Content-Length matches verified artifact, Landing unchanged; (ii) non-Android commit → `android: skipped (no version advancement)` and `ls -l /releases/*.apk` unchanged; (iii) injected failure (duplicate versionCode / corrupt APK) → Android RED, public `release-metadata.json` still references prior SHA.
- **A7 — Deterministic regression evidence for classification, tag pinning, version gating, and failure-closed publication.** The repository has committed tests that fail when the relevant behavior is broken: (a) release-classification unit tests covering A–E union (including C-always-when-migrations), (b) Coolify tag-pinning contract test (asserting PATCH payload uses `sha-…` not `production` and that `production` is not the deploy trigger), (c) Android version gating tests (strict `versionCode` increase, filename pattern, package ID, size bounds, debug rejection), (d) atomic publish failure-closed tests (simulated upload failure → metadata unchanged). Proof: `pnpm test` / `pnpm verify:fast` shows these suites green; mutation of each rule (e.g., downgrade versionCode, replace sha with production) makes the corresponding test fail.

## 3. Confirmed facts, constraints, assumptions, and material unknowns

### Confirmed facts (inspected 2026-08-26)
- `quality.yml` is the canonical quality gate: jobs `static` (fast: tsc+biome+vitest), `backend` (project-verify: 18 real-PB smokes + 3-surface builds + PWA/Android/deploy gates), `e2e` (5 shards), `verify` (merge gate, green only when all lanes green). `release-deploy.yml` already checks the exact commit's `verify` check-run via `gh api repos/.../commits/<SHA>/check-runs`; it blocks a missing/non-green gate.
- `build-images.yml` builds four images (`docker/{landing,app,admin,pocketbase}/Dockerfile`, pinned bases: Node 24.13.0, nginx 1.27.5-alpine, alpine 3.21.4, PB 0.39.9 via `server/VERSION` + sha256) and tags immutably `sha-<12-hex-commit>`; `production` alias historically published post-verification; `latest` never used; digests reported in job summaries.
- Current `release-deploy.yml` is `workflow_dispatch` only (`ref`, `surfaces`, `smoke`, `publish_production_alias`, `environment`), with jobs `resolve → gate-quality → classify → infra-gate → build-images (publish_production_alias=false) → predeploy-backup (B/C only via SSH + FEP_SSH_*) → deploy (PATCH only for staging, Coolify `POST /api/v1/deploy` + poll via `scripts/coolify-deploy.sh`, health via `scripts/prod-health-check.sh`, smoke via `deploy/smoke-prod.sh`, then `publish_production_alias` via `docker buildx imagetools create` ONLY after smoke). `rollback-deploy.yml` PATCHes `docker_registry_image_tag: sha-<image_sha>` + `--force` deploy. This is the baseline to adapt.
- Concurrency today: `release-deploy.yml` uses `group: release-${{ github.ref }}` (per-ref, not per-environment); `build-images.yml` per-ref; `quality.yml` per-workflow+ref. This does **not** prevent two production releases on different refs from overlapping.
- `scripts/release-classify.sh` derives union classes A (landing/app/admin/shared/vite configs), B (pb_hooks/docker/pocketbase/VERSION), C (pb_migrations), D (deploy/docker/scripts/workflows), E (android) from `git diff --name-only <BASE>..<HEAD>` (or whole-tree if no base). Used in `release-deploy` summary and backup gating.
- `scripts/prod-health-check.sh` and `deploy/smoke-prod.sh` are environment-overrideable (`FEP_PROD_HEALTH_*`, `FEP_SMOKE_*`, `FEP_*_RESOLVE`) so staging can fail-closed when overrides are missing (staging guard already exists).
- Landing runtime release resolution: `landing/src/lib/releaseMetadata.ts` fetches same-origin `/releases/release-metadata.json`, validates strictly (filename `fast-english-podcast-vX.Y.Z.apk`, no slashes/debug, version matches `versionName`, package `com.fastenglishpodcast.app`, hex-64 SHA/cert, size bounds), derives `downloadPath = /releases/<fileName>` and `downloadUrl = https://fastenglishpodcast.com/releases/<fileName>` — never trusts an external URL field. `vite.landing.config.ts` serves `releases/` from repo in dev/preview for local fidelity.
- `docker/landing/nginx.conf` serves `/releases/` via `alias /srv/releases/` (host bind mount `/opt/fast-english/shared/releases` read-only), APK `application/vnd.android.package-archive` + `immutable` cache, metadata `max-age=3600`, logs use `$uri` (no query strings), refuses generic `/api/*` (defense in depth — Traefik path route is the true API gateway). Verified in `tests/infra/07-routing-contract.sh` and `08-nginx-redaction.sh`.
- Android version contract: `android/app/build.gradle` (`versionCode 1`, `versionName "1.0.0"`, `applicationId "com.fastenglishpodcast.app"`, `compileSdk/targetSdk` ≤35, AGP 8.7, Gradle 8.12), `capacitor.config.json` appId must match, `package.json` version must equal `versionName` (`scripts/check-android-version.mjs`), `releases/release-metadata.json` must match the same triple. Signing: Gradle `signingConfigs.release` only when `FEP_ANDROID_KEYSTORE_PATH/KEY_ALIAS/KEYSTORE_PASSWORD/KEY_PASSWORD` are set; otherwise `gradle.taskGraph.whenReady` throws `Production signing material: REQUIRED` — no debug-key fallback. `scripts/verify-release-apk.sh` emits `release-metadata.json` + `RELEASE-NOTES.md` after apksigner/zipalign/aapt/sha256.
- Persistent-storage invariant: PocketBase data lives at host `/opt/fast-english/shared/pb_data` (UID 10001) bind-mounted to `/pb/pb_data`; entrypoint refuses to start without it. Proven in `tests/infra/04-pb-persistence.sh` and `05-pb-restore.sh`. `COOLIFY_DEPLOYMENT.md` §8 documents rollback/recovery: frontends = previous image; PB without migration = previous image + same pb_data; PB after migration = stop auto-rollback, restore pre-deploy backup.
- Backup contract: `deploy/backup.sh` (PB Backups API), `deploy/backup-copy.sh` (02:40 UTC timer → `shared/backups` keep 14), `deploy/check-offsite.sh` (off-VPS S3 gate), `deploy/restore-drill.sh`. Backend/migration releases require verified pre-deploy backup + off-VPS gate before deploy.
- GitHub Environments: `release-deploy` and `rollback-deploy` run under `environment: ${{ inputs.environment }}` (`production`/`staging`), pulling secrets from that environment; `staging` health/smoke must define `FEP_PROD_HEALTH_*` + `FEP_SMOKE_*` or fail closed; `STAGING.md` documents isolation.

### Constraints (must hold in any design)
- Canonical quality gate (`quality` → `verify`) for the exact `main` SHA must be green before any production image build/publish or Coolify trigger.
- Production runtime must be the immutable `sha-<commit>` tag, not a moving alias. The alias may be maintained post-verification for traceability but is not the deploy source.
- Selective surface deploy when safely determinable (classification A/B/C/D/E drives backup and target surfaces); a frontend-only change must not cause a PB restart.
- Backup: B/C (hooks/migrations) require verified pre-deploy backup + off-VPS gate via SSH; backup is fail-closed.
- Concurrency: no two production releases overlap; a second push queues.
- Health + smoke are mandatory after any production deploy; any of quality/build/backup/deploy/health/smoke failing is RED/fail-closed (no partial promotion of the alias, no metadata update, no APK overwrite).
- Android: strictly increased `versionCode`, matching `versionName`, stable `applicationId`/signing identity, protected Environment secrets only, verification before publish, staging→atomic publish (never overwrite existing APK bytes), public HTTPS verification of SHA/size, same-origin `/releases/` only.
- Invariants: `/opt/fast-english/shared/pb_data` persistent; migration failure → no blind DB rollback; `PB_ENCRYPTION_KEY` stable; no secrets in repo/bundles/logs/summaries; no `/_/` exposure; no auto-deploy from PRs/unverified commits.

### Assumptions (labeled, to validate in first implementation action)
- A1 — Coolify API PATCH `{"docker_registry_image_tag":"sha-<SHORT>"}` followed by `POST /api/v1/deploy` with `force=true` when re-pinning an already-tagged commit is the reliable way to force a re-pull of the same immutable tag (production will adopt the staging-proven contract; O5 in `COOLIFY_DEPLOYMENT.md` §17).
- A2 — The host path for releases on production is `/opt/fast-english/shared/releases` with an SSH-accessible staging prefix (e.g., `~/.staging` or `/opt/fast-english/shared/releases/.staging`) writable by `FEP_SSH_USER` and readable by the landing container's RO mount.
- A3 — GHCR package names `ghcr.io/<owner>/fast-english/{landing,app,admin,pocketbase}` and the existing `GHCR_PUBLISH_TOKEN`/`GITHUB_TOKEN` flow remain valid; the VPS never builds images.
- A4 — The "base" for release classification diff can safely be the previous `releases/*` tag or, for the initial automated pipeline, `origin/main~1`/previous SHA (fallback to whole-tree on first release is acceptable but must not silently classify as NONE).
- A5 — Android signing material lives (or will live) in the GitHub Environment `production` secrets (`FEP_ANDROID_KEYSTORE_BASE64` or `FEP_ANDROID_KEYSTORE_PATH` plus alias/passwords) via a protected environment (required reviewers), matching the existing Gradle env contract.

### Material unknowns
- U1 — Whether the production Coolify host's SSH user can atomically `mv` within `/opt/fast-english/shared/releases` or whether the landing container's RO mount observes the move instantly (needs a staging-host probe; fallback is a two-phase `cp` + `mv -Tf` with verification).
- U2 — Exact GHCR owner/name for images in the target repository (affects PATCH image refs and first-pull auth).
- U3 — Whether the `staging` environment already defines all required `FEP_*` overrides for fail-closed verification; if not, the automated pipeline must not fall back to production domains.

## 5. Smallest viable design and relevant data / control flow

### Design summary (constraints, not implementation trivia)
- **Trigger:** A new workflow `release-auto.yml` (or an `on: push: branches: [main]` extension with a distinct job graph) runs for every push to `main`. It does not trigger on `pull_request`. Its first job is a hard gate that fetches the `quality` `verify` check-run for the exact `GITHUB_SHA`; if missing/non-green, the workflow exits RED with no side effects. No GHCR publish or Coolify call occurs before this gate.
- **Concurrency:** `concurrency: group: release-production-${{ github.ref == 'refs/heads/main' && 'production' || github.ref }}` (or `group: release-production` when triggered on `main`) with `cancel-in-progress: false` so a second `main` push queues behind the first; staging uses a separate group. This satisfies "do not allow concurrent production releases to overlap" without blocking unrelated branch builds.
- **Immutable-tag deployment (fix alias ordering):** For `environment=production`, the deploy step PATCHes each *affected* Coolify application to `sha-<SHORT>` *before* triggering its deploy (the same contract staging already uses + `force=true`), then polls. Publishing the moving `production` alias (if kept) happens only *after* health+smoke pass, via `docker buildx imagetools create` over the already-verified SHA digests — it is a post-verification convenience, not the runtime source. The workflow never triggers a Coolify deploy that relies on `:production` being pre-moved.
- **Selective surfaces:** `release-classify.sh` determines the surface set when safely determinable. Safe determinable surfaces: A→{landing,app,admin}, B/C→{pocketbase}+ affected A surfaces that changed, E→android only, D→no deploy (config-only → operator action). When classification is ambiguous or spans multiple classes, the conservative fallback is "deploy the four web surfaces together" but still never mutate `pb_data` for a pure-frontend change (verified by the deployment contract tests and by not triggering `pocketbase` when classification is A-only). Manual `workflow_dispatch` (`release-deploy.yml`) remains available for targeted surface retries and for `rollback-deploy.yml`.
- **Backup/recovery preserved:** The `predeploy-backup` job runs for B/C only (same SSH logic as today: `backup.sh` + `backup-copy.sh` + artifact existence check + `check-offsite.sh` off-VPS gate). Its failure fails the workflow before any PB deploy. Rollback/recovery text stays: frontends = previous SHA image; PB without migration = previous SHA image + same `pb_data`; PB after migration = operator-attested restore of pre-deploy backup.
- **Android path (independent from web, but version-gated):** A separate job `android-release` (or workflow `android-release.yml` called from the same `main` push) runs only when E is present *and* version gating passes:
  1) `scripts/check-android-version.mjs` (gradle ↔ capacitor ↔ package.json ↔ existing metadata pattern) + new helper `scripts/android-version-advance.sh` that compares `versionCode`/`versionName` against the last published `releases/release-metadata.json` (from `main` or from the downloaded public metadata) and refuses downgrades/equal codes, debug filenames, or `targetSdk` violations.
  2) `bash scripts/build-release-apk.sh` (requires Environment secrets; no keystore committed).
  3) `bash scripts/verify-release-apk.sh` (apksigner/zipalign/aapt/sha256 → new `release-metadata.json`).
  4) Atomic publication: SSH upload of APK + new `release-metadata.json` + `RELEASE-NOTES.md` to a host staging directory (`/opt/fast-english/shared/releases/.staging/sha-<SHORT>/`), on-host `sha256sum -c` + `stat -c%s` + `aapt`-like filename collision check (`test ! -e final.apk` OR `sha256` equal for idempotent re-run), then atomic promotion (`mv -Tf staging/apk final/apk` and `write-temp + mv -Tf staging/metadata.json final/release-metadata.json`). Partial uploads never become the public download because `release-metadata.json` — the Landing's fetch target — is moved last.
  5) Public verification: `curl --fail` over HTTPS on `https://fastenglishpodcast.com/releases/<file>` checking `Content-Length` + `sha256sum` of downloaded bytes equals verified artifact, plus `release-metadata.json` SHA/size/200 JSON body. Old APK files are never deleted. If version was not advanced appropriately, the job exits 0 with `skipped (no version advancement)` and web deployment proceeds independently (web success ≠ Android success).
- **Failure-closed:** Every gate (quality, build, backup, Android verify, Coolify deploy, health, smoke, APK publish) has an explicit non-zero exit that makes the workflow RED; no subsequent promotion (alias update, metadata move, APK finalization) runs after a failure; staging files are cleaned up; the previously published APK/metadata stay current.

### Relevant data/control flow (happy path)
```
push to main (SHA abc123, versionName X.Y.Z, versionCode N)
  → gate-quality: gh api check-runs for abc123, job `verify` must be success
  → classify: git diff BASE..abc123 → classes (e.g., "A C E")
  → infra-gate: pnpm test:infra:coolify on abc123
  → build-images: 4 images ghcr.io/...:sha-abc123 (digests), summary
  → predeploy-backup (if B/C): SSH backup + off-VPS gate
  → deploy (production, per affected surface):
       PATCH coolify app {docker_registry_image_tag: sha-abc123}
       POST /api/v1/deploy {uuid, force:true} → deployment_uuid
       poll GET /api/v1/deployments/<uuid> → finished (or RED)
  → health: curl public domains (FEP_PROD_HEALTH_*, real PB JSON bodies)
  → smoke: deploy/smoke-prod.sh --quick (or --full when creds present)
  → verdict GREEN; optionally re-point :production alias to sha-abc123
  ── if E and version advances (N > prior N):
  → android: check-android-version + version-advance → build signed APK
       → verify-release-apk → staging SSH upload → host integrity
       → atomic mv to /releases/ + public HTTPS verification
       → GREEN (web) + android GREEN; else android SKIPPED/RED independently
```

## 6. Security, correctness, performance, UX, migration, reliability, recovery, and rollback risks

- **Security:** Android signing material must stay in protected GitHub Environment secrets (or another approved secret mechanism already in use); keystore bytes/passwords must never appear in repo, build artifacts, logs, frontend bundles, or workflow `GITHUB_STEP_SUMMARY` (only digests/SHA-256/size/version are logged). `PB_ENCRYPTION_KEY` stability across releases (must not be rotated without re-encrypting settings and updating both host file and Coolify env, as proven by `tests/infra` and `STAGING.md` F17). Preserve same-origin `/releases/` (no external URL from metadata), Landing `GET /api/fast-english/public/settings` remains the only landing API route (nginx + Traefik both refuse generic `/api/*`). `/_/` stays 404 via routing-contract tests. Mitigation: secret-scan + token-redaction proofs remain in the quality gate; workflow steps redact secrets and use 0600 header files (existing `coolify-deploy.sh` pattern).
- **Correctness:** Exact-SHA gating: `GITHUB_SHA` must match the `quality` `verify` run's `head_sha` (not merely the latest `main`). Immutability: Coolify PATCH payload must be `sha-<SHORT>` derived from `git rev-parse HEAD` at that SHA, not from `GITHUB_REF_NAME`. Android filename immutability: `fast-english-podcast-vX.Y.Z.apk` must match `versionName`; existing file with same name but different bytes must be refused (compare SHA before `mv`). Concurrency: `release-*` groups must be environment-scoped, not per-ref, or parallel production runs can race the backup/deploy/publish sequence. Idempotency: re-running the same SHA must not duplicate `sha-…` tags or overwrite an existing APK with different bytes (safe to skip when SHA matches).
- **Migration/recovery:** Pre-deploy backup required for B/C; `predeploy-backup` must complete *before* any PB Coolify PATCH/deploy. Migration class C must surface the non-reversibility warning in the workflow summary and link to `docs/BACKUP_RESTORE.md` §5. Blind DB rollback on failure is forbidden — recovery is either previous-image redeploy (no migration) or explicit restore of the verified pre-deploy backup (with migration). `/opt/fast-english/shared/pb_data` must remain a bind mount, never replaced by Coolify automation.
- **Reliability/rollback:** Coolify deploy must be polled to a terminal state (`finished`/`failed`/`cancelled-by-user`); a `failed` or timeout must be RED with an exact next action (check dashboard log; `rollback-deploy.yml` with previous `sha-…` for frontends/PB-without-migration; restore backup for PB-with-migration). Deployment of frontends must not trigger a PB restart (proven by container start-time checks). Backup freshness and host disk must be checked before promotion (existing `ops-check` checks cover this).
- **Performance:** Building four images concurrently (pinned base layers cached via `cache-from/to: type=gha`) keeps the pipeline under typical GHCR/Actions limits; no image is built on the VPS. Health/smoke timeouts must be bounded (`FEP_HEALTH_TIMEOUT`, deploy poll timeout 1200 s) to avoid hanging the concurrency queue.
- **UX:** Landing's honest states must survive the new flow: when Android metadata is temporarily absent or invalid, the Landing shows the "not released yet" state (existing `siteConfig`/`releaseMetadata` behavior), not a broken link. No user-visible change to Student/Admin flows during a release beyond the normal deploy window.
